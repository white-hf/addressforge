# 证据驱动的循环开发方法论

## 文档信息

- 文档类型：通用项目开发与 Agent 执行方法论
- 适用对象：软件工程师、产品工程团队、技术负责人、AI 开发 Agent
- 适用项目：新项目、存量系统、数据平台、API、自动化系统、机器学习与 AI 项目
- 状态：Active

## 1. 文档目的

本文定义一套可复用的项目开发方法，使新的工程团队或开发 Agent 能够：

- 先理解问题，再开始实现
- 用真实证据决定开发优先级
- 将复杂目标拆成可验证的小迭代
- 保持产品目标、系统设计、代码和验证结果一致
- 避免无依据优化、局部补丁堆积和架构漂移
- 在每轮开发后明确判断：继续、调整、发布、回滚或停止

本文不规定具体编程语言、框架、数据库或模型类型。项目可以根据自身情况替换技术栈，但不应跳过证据、验证、比较和复盘环节。

## 2. 一句话总纲

**开发不是持续增加代码，而是持续减少对问题、方案、风险和结果的不确定性。**

一个完整开发循环是：

```text
理解目标
  → 检查真实现状
  → 收集证据
  → 识别失败模式
  → 定义明确需求
  → 选择技术方法
  → 实现最小完整切片
  → 验证真实结果
  → 对比基线
  → 复盘残余问题
  → 决定下一轮
```

任何缺少“证据、需求、验证或基线比较”的代码改动，都不构成完整迭代。

## 3. 核心开发原则

### 3.1 目标优先于动作

开始工作前必须明确：

- 谁遇到了什么问题
- 为什么值得解决
- 期望改变什么结果
- 当前范围是什么
- 明确不做什么
- 如何判断成功

“开发一个功能”“训练一个模型”“优化一个接口”只是动作，不是目标。

合格目标应描述结果，例如：

- 减少用户完成关键流程的失败
- 降低高风险操作的错误率
- 提高系统在目标负载下的稳定性
- 降低人工处理成本，同时保持质量不回退

### 3.2 真实证据优先于直觉

开发决策应优先依据：

- 真实用户行为
- 生产数据
- 日志、监控和追踪
- 数据库状态
- 错误报告和支持记录
- 基准测试
- 可复现样本
- 用户或运营反馈

直觉可以形成假设，但不能直接形成结论。

### 3.3 先定义问题，再选择方案

不要因为熟悉某项技术，就把所有问题都解释成适合该技术的问题。

在选方案前，先判断根因属于：

- 产品或流程问题
- 数据质量问题
- 业务规则问题
- 实现缺陷
- 架构边界问题
- 性能或容量问题
- 依赖或环境问题
- 模型或算法问题
- 可观测性不足
- 文档和操作问题

不同根因需要不同方法。错误分类会导致高成本、低收益的开发。

### 3.4 小步完成，端到端验证

优先交付最小完整切片：

- 有明确需求
- 有必要设计
- 有实际实现
- 有测试与验证
- 有结果记录
- 可以独立判断成败

不要长期只建设某一横向层而没有可验证结果。例如，只写大量基础设施、只补测试、只做 UI、只训练模型，都可能形成无法闭环的半成品。

### 3.5 比较变化，而不是只报告当前值

“现在是多少”不等于“是否改善”。

每次迭代至少要回答：

- 基线是什么
- 新结果是什么
- 差值是多少
- 哪些样本变好了
- 哪些样本变差了
- 改善来自哪里
- 是否引入新的风险

### 3.6 测试通过不等于目标达成

代码编译、静态检查和单元测试是必要条件，但不是完成条件。

需求完成还需要：

- 目标行为真实发生
- 关键指标满足要求
- 代表性样本得到改善
- 非目标区域没有不可接受回退
- 运行环境与验证环境一致或差异已说明
- 剩余风险得到记录

### 3.7 发布是一个阶段，不是一个按钮

高风险改动应逐级推进：

```text
离线实验
  → 测试环境
  → 影子运行
  → 辅助建议
  → 受控影响
  → 小流量发布
  → 全量发布
```

每一级都应定义：

- 进入条件
- 观察指标
- 失败条件
- 回滚方式
- 负责人或审批人

### 3.8 文档是系统状态的一部分

文档不是开发结束后的装饰。

文档应分别记录：

- 为什么做
- 系统应该如何工作
- 本轮准备怎么做
- 实际做了什么
- 如何验证
- 还剩什么

代码和文档长期不一致时，团队将失去可靠决策基础。

## 4. 新项目或新 Agent 入场协议

新的开发者或 Agent 不应直接从待办事项开始编码。

### 4.1 第一步：建立目标上下文

阅读并提取：

- 项目愿景
- 用户和使用场景
- 当前阶段目标
- 非目标
- 成功指标
- 安全、隐私和合规边界

如果这些内容不存在或互相矛盾，应先补充问题定义或请求决策。

### 4.2 第二步：建立文档地图

识别以下文档是否存在：

- 产品需求
- 系统设计
- 当前迭代计划
- 最近执行总结
- 开发者工作流
- 测试策略
- 发布与回滚流程
- Agent 工作规则

需要知道每类决策由哪份文档负责，避免同一规则散落在多个位置。

### 4.3 第三步：检查代码和运行环境

至少确认：

- 项目目录结构
- 主入口
- 配置加载方式
- 数据存储
- 外部依赖
- 测试命令
- 构建和启动方式
- 当前分支和工作区状态
- 本地、测试、生产环境差异
- 敏感信息和权限边界

不要硬编码已经由配置系统管理的值。

### 4.4 第四步：建立可复现基线

在改变系统前记录：

- 当前版本或提交
- 当前配置标识
- 当前数据集或样本范围
- 当前关键指标
- 当前错误分布
- 当前已知问题
- 当前运行时身份

没有基线，就无法证明后续变化来自本轮实现。

### 4.5 第五步：选择关键路径上的最小需求

优先选择：

- 阻塞其他工作的基础问题
- 有真实证据支持的问题
- 可以在一个迭代内闭环的问题
- 对总目标有实质影响的问题

不要优先选择：

- 最容易写的功能
- 最显眼但不关键的 UI 问题
- 没有用户价值的重构
- 只有单个案例支持的规则补丁

## 5. 文档分层与责任

### 5.1 产品需求文档

负责：

- 用户问题
- 价值主张
- 用户流程
- 范围和非目标
- 产品级成功标准

不负责具体代码实现。

### 5.2 系统设计文档

负责：

- 当前状态与目标状态
- 架构层次
- 组件责任
- 接口和数据合同
- 安全边界
- 发布和回滚模式
- 长期技术约束

架构发生变化时，应先更新系统设计。

### 5.3 迭代执行计划

负责一个有边界的阶段：

- 背景和问题
- 阶段目标
- 具体需求
- 技术方法
- 交付物
- 完成标准
- 风险与依赖

迭代计划不能只列文件和函数。

### 5.4 执行总结

负责记录事实：

- 实际实现
- 实际验证
- 指标变化
- 样本变化
- 偏离计划的地方
- 剩余风险
- 下一步建议

总结不应把预测收益写成实际结果。

### 5.5 Agent 或团队治理文档

负责：

- 代码修改规则
- 验证要求
- 数据和权限规则
- 文档更新要求
- 发布审批规则
- Agent 的停止、升级和人工确认条件

### 5.6 多层变更的更新顺序

当工作跨越多个层次时，按以下顺序更新：

1. 产品或问题定义
2. 系统设计
3. 迭代计划
4. 代码与配置
5. 验证产物
6. 执行总结

## 6. 证据驱动的完整迭代循环

### 6.1 阶段一：检查真实现状

检查范围根据项目类型选择：

- 生产或测试数据库
- 用户事件
- 日志和异常
- 服务指标
- 队列和积压
- 当前发布版本
- 配置和功能开关
- 模型或规则产物
- 最近测试和发布记录
- 用户反馈和人工处理结果

输出：

- 当前状态摘要
- 数据来源和时间范围
- 已确认事实
- 尚未确认的假设

### 6.2 阶段二：识别失败模式

不要直接从“结果不好”跳到“修改代码”。

应对失败进行分桶，例如：

- 输入缺失
- 状态不一致
- 边界条件错误
- 数据污染
- 分类错误
- 召回不足
- 排序错误
- 并发竞争
- 缓存过期
- 依赖失败
- 权限失败
- 性能退化
- 用户流程中断

每个失败桶应回答：

- 发生频率
- 影响用户或业务
- 代表性样本
- 可复现条件
- 可能根因
- 是否与其他失败桶共享根因

### 6.3 阶段三：形成问题判断

将事实、推断和未知分开：

| 类型 | 含义 |
|---|---|
| 事实 | 已由数据、日志、代码或复现确认 |
| 推断 | 根据事实形成但尚未完全验证的解释 |
| 未知 | 当前证据不足，需要继续调查 |

不要把推断写成事实。

如果证据不足，应优先补可观测性或建立最小复现，而不是直接修改核心逻辑。

### 6.4 阶段四：定义下一项需求

一个合格需求至少包含：

- 需求名称
- 问题陈述
- 用户或系统目标
- 当前基线
- 目标指标或验收行为
- 技术方法类别
- 范围
- 非范围
- 回归风险
- 验证方法

推荐模板：

```markdown
### 需求名称

问题：

证据：

目标：

技术方法：

预期收益：

保护指标或不变量：

范围：

非范围：

验证方法：

完成标准：

风险：
```

### 6.5 阶段五：选择技术方法

技术方法描述应说明“如何改变系统行为”，而不只是“修改哪个文件”。

合格描述示例：

- 使用幂等键消除重复执行
- 使用状态机约束非法状态迁移
- 使用缓存版本戳避免读取过期配置
- 使用分层采样纠正数据分布偏差
- 使用候选召回与重排分离召回和精度问题
- 使用读写隔离降低并发竞争
- 使用渐进式开关控制高风险行为
- 使用结构化错误码替代字符串推断

文件、类和函数只是实现位置，不是技术方法本身。

### 6.6 阶段六：设计最小完整切片

切片应同时满足：

- 对目标有实质贡献
- 可以独立验证
- 风险边界清楚
- 不需要一次完成整个长期路线

典型切片包括：

- 一个端到端用户流程
- 一个可独立上线的 API 行为
- 一个可验证的数据处理阶段
- 一个影子运行的模型或策略
- 一个带监控和回滚的功能开关

### 6.7 阶段七：实施

实施期间应遵守：

- 先检查工作区，保护已有修改
- 避免无关重构
- 保持接口、数据和版本合同明确
- 为风险路径增加日志和可观测性
- 对不可恢复操作格外谨慎
- 使用迁移、版本和兼容策略保护现有数据
- 新增行为同时补充相应测试

如果实现过程中发现原需求判断错误，应暂停并更新需求，不要悄悄扩大范围。

### 6.8 阶段八：分层验证

验证强度应与风险匹配。

### 第一层：静态和局部验证

- 格式化
- 静态检查
- 类型检查
- 编译
- 单元测试

### 第二层：组件和集成验证

- 服务间调用
- 数据库交互
- 消息和任务流
- 序列化与反序列化
- 权限和鉴权
- 错误处理

### 第三层：回归验证

- 已知失败案例
- 核心用户路径
- 历史高风险边界
- 性能与容量
- 兼容性

### 第四层：真实环境验证

- 真实数据
- 真实依赖
- 真实产物
- 真实请求路径
- 真实监控
- 真实回放或影子流量

不能运行某一层验证时，必须明确说明：

- 未运行什么
- 为什么
- 风险是什么
- 后续由谁、在何环境补充

### 6.9 阶段九：对比基线

至少比较：

- 关键指标前后值
- 错误桶前后数量
- 代表性样本前后输出
- 性能和资源变化
- 新增失败
- 非目标区域回归

同时解释收益来源：

- 业务规则
- 算法或模型
- 数据质量
- 样本分布
- 候选质量
- 缓存或性能优化
- 架构调整

### 6.10 阶段十：复盘与下一轮决策

每轮结束后选择一个明确结论：

- 需求完成，可以关闭
- 仍在同一问题边界内，继续当前迭代
- 瓶颈转移，开启新迭代
- 需要更多数据或人工确认
- 方案假设不成立，应回退或重设计
- 收益不足，不继续投入
- 风险超标，回滚

不要因为已经投入很多时间而继续错误方向。

## 7. 基线与可复现性

### 7.1 基线必须可识别

基线至少应包含：

- 代码版本
- 配置版本
- 数据版本
- 依赖版本
- 运行环境
- 测试或评估命令
- 指标和报告

### 7.2 产物必须可追溯

重要产物应记录：

- 生成时间
- 输入来源
- 生成代码版本
- 配置
- 数据或快照标识
- 文件哈希
- 上下游版本

### 7.3 不可变版本优于可变别名

正式评估和发布应引用不可变版本。

可变名称可以作为方便入口，但不能作为唯一审计依据。例如，“latest”“current”“default”必须能够解析到唯一的不可变版本。

### 7.4 训练、评估和运行必须使用同一合同

对于数据、算法或模型系统，应保证：

- 特征定义一致
- 字段语义一致
- 缺失值处理一致
- 版本一致
- 运行时加载的是被评估的同一产物

任何 fallback 都必须被记录，不能静默切换到其他版本。

## 8. 测试策略

### 8.1 单元测试

适合：

- 纯函数
- 边界条件
- 状态转换
- 数据转换
- 错误处理

### 8.2 集成测试

适合：

- 数据库
- 外部服务
- 队列
- 文件产物
- 多模块合同
- API 请求与响应

### 8.3 回归测试

每个已确认的重要缺陷都应尽量留下可复现测试。

回归测试应描述：

- 原始失败
- 预期行为
- 为什么该行为重要

### 8.4 端到端测试

适合验证：

- 用户关键路径
- 发布后完整流程
- 多服务协作
- 真实权限和配置

### 8.5 性能和可靠性测试

高负载或关键系统还应测试：

- 延迟
- 吞吐
- 内存和存储增长
- 并发
- 重试
- 幂等
- 故障恢复
- 降级

## 9. 发布、门控与回滚

### 9.1 发布姿态

每项高风险能力必须明确处于哪一阶段：

| 阶段 | 系统影响 |
|---|---|
| Offline | 不接触运行流量 |
| Shadow | 处理真实输入，但不影响正式结果 |
| Assist | 只提供建议，由用户或现有逻辑决定 |
| Guarded | 仅在安全条件内影响结果 |
| Partial Rollout | 影响受控比例用户或流量 |
| Default On | 成为默认行为 |

### 9.2 发布门槛

发布门槛至少覆盖：

- 功能正确性
- 回归风险
- 性能
- 可靠性
- 可观测性
- 产物完整性
- 配置和版本一致性
- 回滚可行性

缺失关键指标应视为阻塞，而不是自动通过。

### 9.3 回滚设计

上线前必须知道：

- 回滚到哪个版本
- 如何触发
- 是否涉及数据迁移
- 是否需要清理缓存
- 是否兼容旧数据
- 如何验证回滚成功

回滚不能只存在于文档中，应在合适环境演练。

## 10. 数据与机器学习项目的附加原则

### 10.1 数据质量是产品能力

训练数据不是算法实现的附属品。

必须治理：

- 来源
- 标签语义
- 去重
- 冲突
- 缺失
- 分布
- 时间漂移
- 数据泄漏
- 人工审核质量

### 10.2 困难样本不等于真实分布

应区分：

- 纠错样本
- 校准样本
- 随机生产样本
- 新鲜样本
- 历史样本
- 冻结验证样本

只使用最困难样本训练和评估，会使模型偏离真实生产分布。

### 10.3 冻结验证集

用于发布判断的验证集应：

- 版本固定
- 不参与训练
- 来源可追溯
- 覆盖主要场景和高风险边界
- 在必要时通过正式流程升级版本

### 10.4 不以单一指标决定模型质量

至少联合考虑：

- 总体质量
- 关键类别质量
- 少数类质量
- 误报和漏报
- 人工处理成本
- 性能
- 稳定性
- 数据漂移

### 10.5 从对照到影响

推荐演进：

```text
规则或旧模型基线
  → 新模型离线比较
  → 真实回放
  → 影子运行
  → 辅助建议
  → 安全守卫内影响
  → 逐步扩大
```

### 10.6 实验不等于交付

实验应明确：

- 假设
- 数据
- 方法
- 指标
- 结果
- 是否进入产品路线

没有版本化产物、运行时合同、发布门槛和回滚方案的模型，只是实验产物。

## 11. 人工决策与自动化边界

### 11.1 明确权威来源

对高风险判断，应定义最终权威是：

- 用户
- 业务专家
- 审核人员
- 外部权威系统
- 经批准的自动化规则

### 11.2 自动化不得伪装成人工决策

自动生成内容应使用真实语义，例如：

- draft
- suggested
- machine_generated
- pending_review

不得未经人工确认就标记为：

- human_confirmed
- approved
- final

### 11.3 需要人工门槛时

Agent 应：

1. 明确通知需要人工处理
2. 准备必要证据和候选方案
3. 可以继续做不改变最终权威状态的支持工作
4. 等待确认后再推进受影响的训练、发布或正式数据变更

## 12. Agent 执行规则

### 12.1 开始前

Agent 应：

- 阅读项目目标和当前迭代
- 阅读仓库级工作规则
- 检查工作区状态
- 识别权限和安全边界
- 确认任务属于分析、诊断、修改还是发布

### 12.2 工作中

Agent 应：

- 说明关键假设
- 定期报告进度和中间证据
- 保护用户已有修改
- 不扩大未授权范围
- 优先使用可逆操作
- 对破坏性或外部影响操作请求确认
- 遇到证据与原计划冲突时及时调整

### 12.3 结束时

Agent 应说明：

- 完成了什么
- 修改了什么
- 如何验证
- 未验证什么
- 剩余风险
- 下一步是什么

不要只列文件名，也不要只说“任务完成”。

## 13. 完成标准与停止条件

### 13.1 单项需求完成

只有同时满足以下条件才算完成：

- 实现完成
- 测试完成
- 真实行为或强证据验证完成
- 已与基线比较
- 回归风险已检查
- 文档已更新
- 剩余问题已记录

### 13.2 迭代完成

迭代完成还要求：

- 所有范围内需求关闭
- 交付物齐全
- 完成标准全部满足
- 发布姿态明确
- 下一依赖明确

### 13.3 项目目标完成

项目不是因为“没有更多代码要写”而完成。

项目完成要求：

- 总目标已实现
- 用户或业务结果达到约定标准
- 系统达到约定发布阶段
- 关键风险低于可接受阈值
- 关键路径上没有未完成迭代

### 13.4 合理停止条件

可以停止或升级给用户的情况：

- 目标已经完成
- 用户明确暂停
- 需要新的产品或业务决策
- 缺少必要权限
- 外部依赖不可用
- 需要真实人工审核
- 安全或合规边界不允许继续
- 目标和验收标准互相矛盾

不能因为以下原因停止：

- 刚完成一个函数
- 单元测试刚通过
- 文档刚更新
- 当前实现比较困难
- 还需要进一步调查

## 14. 常见反模式

### 14.1 先写代码，再寻找问题

结果：产生无价值功能和架构漂移。

### 14.2 用单个案例驱动全局规则

结果：修复一个样本，破坏更大分布。

### 14.3 只看总体平均指标

结果：少数类、高风险用户和关键路径被掩盖。

### 14.4 只使用困难样本作为训练或评估分布

结果：系统对边界过敏，偏离真实流量。

### 14.5 把测试通过当作需求完成

结果：代码正确，但产品结果没有改善。

### 14.6 只报告新结果，不报告基线

结果：无法判断变化是否有效。

### 14.7 静默 fallback

结果：评估和运行使用了不同版本，却无法追溯。

### 14.8 跳过影子和受控发布

结果：离线表现直接变成生产事故。

### 14.9 用自动化结果冒充人工确认

结果：监督数据和业务事实失去可信度。

### 14.10 无限扩展当前迭代

结果：范围失控、完成标准不断移动。

### 14.11 频繁切换到非关键工作

结果：核心问题长期不闭环，项目看似繁忙但没有收敛。

### 14.12 只写“优化了一轮”

结果：后续人员不知道需求、方法、收益和残余风险。

- [ ] 我读过产品、设计、当前计划和最近总结
- [ ] 我知道代码、测试、配置和运行入口
- [ ] 我检查过工作区和权限边界
- [ ] 我建立了可复现基线

- [ ] 问题有真实证据
- [ ] 失败模式已经分类
- [ ] 需求有名称和完成标准

- [ ] 保护指标和回归风险已经定义
- [ ] 该需求属于当前迭代

### 实施后

- [ ] 单元测试通过
- [ ] 集成或回归验证完成
- [ ] 真实环境或真实数据已验证，或缺口已说明
- [ ] 新旧基线已比较

- [ ] 文档已同步

- [ ] 发布阶段明确
- [ ] 门槛全部通过

## 18. 推荐的最小项目治理结构

成熟结构可按项目特点调整；新项目至少应有：

```text
AGENTS.md
docs/
  prd/
  design/
  iterations/
  summaries/
  runbooks/
  developer-workflow.md
  testing-strategy.md
  release-process.md
tests/
  unit/
  integration/
  regression/
scripts/
```

目录不是目标，责任边界才是目标。已有成熟结构不应仅为符合模板而重构。

## 19. 方法论的最终判断标准

采用本方法后，一个健康项目应当能够回答：

- 当前最重要的问题是什么？
- 证据是什么？
- 为什么现在解决它？
- 本轮需求和非范围是什么？
- 使用了什么技术方法？
- 与基线相比发生了什么变化？
- 哪些风险得到验证？
- 当前处于什么发布阶段？
- 如果失败，如何回滚？
- 下一轮为什么做这件事？

如果团队或 Agent 无法回答这些问题，说明项目仍在依赖活动量而不是结果推进。

真正有效的循环开发，应让每一轮都产生三类沉淀：

1. 更可靠的系统
2. 更清楚的事实
3. 更好的下一步决策
